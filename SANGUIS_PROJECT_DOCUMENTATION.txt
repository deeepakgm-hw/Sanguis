1. EXECUTIVE SUMMARY & PROJECT OVERVIEW
--------------------------------------------------------------------------------
Project Name   : Sanguis
Tagline        : Connect Donors, Respond to Emergencies, Save Lives in Real-Time
Target Audience: Emergency Blood Donors, Hospitals, Trauma Centers, Blood Banks, Recipients
Design System  : Crimson Red & Pure White Split-Hero Aesthetic with Indian Hackathon Branding
Repository URL : https://github.com/deeepakgm-hw/Sanguis

Sanguis is an enterprise-grade, production-quality emergency blood matching and regional shortage 
forecasting platform. Designed to meet the stringent standards of top tech organizations (Google, 
Stripe, Razorpay, Amazon), Sanguis bridges the critical gap between emergency blood requests from 
hospitals and eligible local donors.

Key Value Propositions:
- Real-Time Geospatial Matching: Uses GPS Haversine calculations to match emergency hospital requests 
  with nearby eligible donors within minutes.
- Predictive Shortage Forecaster: Analyzes 14-day demand trends against regional inventory and donor 
  density to calculate shortage risk tiers (Healthy, Watch, Critical).
- Starvation-Free Priority Queue: Computes a multi-factor priority score (Urgency + Wait Time + Units 
  Needed + Verification Bonus) so low-urgency requests do not suffer from indefinite starvation.
- Canonical AABB Eligibility Engine: Enforces the 90-day whole-blood medical interval alongside 
  voluntary donor blackout period management.
- Production Authentication & SMTP OTP: Direct 6-digit OTP verification via Gmail SMTP with bcrypt 
  password/OTP hashing, 5-minute expiration, and rate-limited resend controls.

3. CORE ALGORITHMS & DOMAIN LOGIC
================================================================================

A. AABB Medical Re-eligibility & Voluntary Availability Engine
--------------------------------------------------------------
File: backend/src/services/eligibility.service.ts
- Canonical Interval: WHOLE_BLOOD_ELIGIBILITY_DAYS = 90 (single source of truth across system).
- Formula:
  nextEligibleDate = lastDonationDate + (90 * 24 * 60 * 60 * 1000)
  daysUntilEligible = Math.ceil((nextEligibleDate - now) / 86400000)
- Voluntary Availability: Donors can define temporary unavailability windows (e.g. travel, illness).
- Combined Matching Check: A donor is matching-eligible ONLY IF:
  1) Medical interval (90 days) has elapsed.
  2) No active voluntary blackout window overlaps with current timestamp.

B. Multi-Factor Priority Dispatch Scoring System
--------------------------------------------------
File: backend/src/services/priority.service.ts
Formula: Total Priority Score = Urgency Score + Wait-Time Score + Shortfall Score + Verification Bonus
- Urgency Score     : Critical = 100 | High = 60 | Medium = 30 | Low = 10
- Wait-Time Score   : +3 points per hour waiting, capped at 50 points (~17 hours) to prevent starvation.
- Shortfall Score   : +4 points per unit needed, capped at 40 points (≥10 units).
- Verification Bonus: +15 points for verified hospital requesters.
- Max Possible Score: 205 points.

C. AI Shortage Forecasting Engine
---------------------------------
File: backend/src/services/forecast.service.ts
- Analysis Window: 14 days lookback for regional demand rate.
- Calculation:
  1) projectedWeeklyDemand = (recentRequestsInRadius / 14) * 7
  2) combinedSupply = bankInventoryUnitsInRadius + eligibleDonorCountInRadius
  3) ratio = combinedSupply / max(projectedWeeklyDemand, 1)
- Risk Tiers:
  - Ratio ≥ 3.0 → HEALTHY ("Stable Supply")
  - 1.5 ≤ Ratio < 3.0 → WATCH ("Monitor Closely")
  - Ratio < 1.5 → CRITICAL ("Critical Shortage")

D. Geospatial Matching Engine
-----------------------------
File: backend/src/services/matching.service.ts
- Calculates Haversine distance in kilometers between hospital GeoJSON Point coordinates and candidate donor coordinates.
- Filters candidates by blood type compatibility (e.g. O- universal donor, exact match preference).

4. DATABASE SCHEMAS & MODELS
================================================================================

1. User Model (backend/src/models/User.ts)
   - _id, name, email (unique), phone (unique, sparse), password, role ('donor'|'hospital'|'user'|'admin'),
     isEmailVerified, googleId, githubId, createdAt, updatedAt.

2. PendingRegistration Model (backend/src/models/PendingRegistration.ts)
   - email, name, firstName, lastName, phone, passwordHash, role, otpCode, otpHash (bcrypt),
     otpExpiry (5 min), verificationAttempts (max 5), resendCount (max 5), lastResendAt, status ('PENDING'|'VERIFIED'|'EXPIRED').

3. Donor Model (backend/src/models/Donor.ts)
   - userId (ref User), bloodType ('A+'|'A-'|'B+'|'B-'|'AB+'|'AB-'|'O+'|'O-'), lastDonationDate,
     medicalFlags (array), location (GeoJSON Point: [lng, lat]), trustScore (0-100), createdAt, updatedAt.

4. DonorAvailability Model (backend/src/models/DonorAvailability.ts)
   - donor (ref Donor, unique), unavailablePeriods: [{ _id, from, to, reason }].

5. Hospital Model (backend/src/models/Hospital.ts)
   - hospitalId (ref User), name, formattedAddress, contactPhone, phoneNumber, isVerified,
     dataSource ('google_places'|'manual'), location (GeoJSON Point).

6. BloodBank Model (backend/src/models/BloodBank.ts)
   - name, address, location (GeoJSON Point), contactPhone, isVerified, owner (ref User),
     inventory: [{ bloodType, unitsAvailable, lastRestocked }].

7. BloodRequest Model (backend/src/models/BloodRequest.ts)
   - hospital (ref User), hospitalName, bloodType, unitsNeeded, urgencyLevel ('critical'|'high'|'medium'|'low'),
     status ('open'|'matched'|'fulfilled'), description, geoLocation (GeoJSON Point), createdAt.

8. Match Model (backend/src/models/Match.ts)
   - request (ref BloodRequest), donor (ref Donor), status ('pending'|'accepted'|'declined'|'expired'), respondedAt.

9. Notification Model (backend/src/models/Notification.ts)
   - user (ref User), title, message, type ('info'|'success'|'warning'|'error'), isRead, createdAt.

10. UserPreferences Model (backend/src/models/UserPreferences.ts)
    - userId (ref User), emergencyAlerts, donationReminders, newMessages, shareLocation.

6. REST API REGISTRY & ENDPOINTS
================================================================================

AUTHENTICATION & OTP (`/api/v1/auth`)
- POST   /api/v1/auth/register       : Create pending registration & send 6-digit SMTP OTP.
- POST   /api/v1/auth/verify-otp     : Verify 6-digit OTP code, promote to User, issue JWT access/refresh tokens.
- POST   /api/v1/auth/resend-otp     : Resend 6-digit OTP email with 60s rate-limit cooldown.
- POST   /api/v1/auth/login          : User sign in with email/password.
- GET    /api/v1/auth/google         : Google OAuth authentication endpoint.
- GET    /api/v1/auth/github         : GitHub OAuth authentication endpoint.
- POST   /api/v1/auth/logout         : Clear authentication cookies & revoke refresh token.

DONOR AVAILABILITY (`/api/v1/donors`)
- GET    /api/v1/donors/me/availability         : Fetch donor medical eligibility & voluntary blackout periods.
- POST   /api/v1/donors/me/availability         : Add voluntary unavailability date range (`from`, `to`, `reason`).
- DELETE /api/v1/donors/me/availability/:id     : Remove voluntary unavailability period.

FORECAST & SYSTEM (`/api/v1/forecast`, `/api/v1/seed`, `/api/v1/health`)
- GET    /api/v1/forecast            : Fetch regional shortage forecast by blood type & coordinates.
- POST   /api/v1/seed                : Trigger on-demand database re-seeding with 10 Indian emergency hospitals & 50 donors.
- GET    /api/v1/health              : Server & database health status check.

8. RUNNING THE APPLICATION LOCALLY
================================================================================

1. Navigate to backend directory: cd backend
2. Install dependencies: npm install

   (Server runs on http://localhost:5000)

2. Install dependencies: npm install
